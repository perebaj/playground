# magnolia-quack-poc

A self-contained POC that validates the Magnolia Query Engine design end-to-end on a laptop, using synthetic data. No private OllyGarden data is involved.

The goal: prove that (1) parquet fixtures in the proposed org-first hive layout can be read by a Quack server, (2) clients can connect via Quack RPC and run typed + analytical queries, (3) per-org isolation is the responsibility of the calling layer (Olive), not Quack itself.

## What it does

1. Generates lightweight parquet fixtures matching the magnolia 5-table schema (`traces`, `logs`, `metrics_gauge`, `metrics_sum`, `metrics_histogram`) for three synthetic orgs across two dates.
2. Boots a Quack server on `localhost:9494` with views over the fixtures.
3. Runs a smoke suite of queries that mirrors the typed and analytical endpoint patterns the design doc proposes.

## Local flow (no kind required)

```
make build      # compile cmd/fixture-gen
make fixtures   # generate ./fixtures/org_id=*/tables/{signal}/date=*/data.parquet
make serve      # start local Quack server in the background
make smoke      # run the smoke query suite against the server
make stop       # stop the server
```

`make all` runs the whole sequence (fixtures → serve → smoke → stop).

## What the smoke suite proves

```
1. table counts                     all 5 views resolve to expected counts
2. per-org-per-date span count      hive partitioning exposes org_id and date
3. typed /services per org          one-org filter behaves
4. /attributes/cloud.platform       JSON attribute extraction works
5. partition pruning sanity         date filter narrows to a single parquet
6. cross-org admin query            server allows it when no org filter
7. per-org isolation check          server returns ANY org the SQL asks for
```

## Findings

- The Quack server is happy executing whatever SQL the client sends.
- Quack does NOT enforce per-org boundaries on its own. A query for `WHERE org_id IN ('alpha', 'beta')` returns both orgs' data. **Per-org isolation must live in the Olive translation layer** (rewriting WHERE on every typed endpoint, gating SQL passthrough to admin-only).
- DuckDB hive partitioning + Parquet reads work directly against the proposed storage layout. The 5-table schema generated by `fixture-gen` matches the column types of `magnolia-sampler/internal/duckdb/schema.go`.
- The Quack extension binds to `localhost` by default; serving on `0.0.0.0` requires the `allow_other_hostname := true` parameter to `quack_serve()` (not a SET pragma).
- The official `duckdb/duckdb` image on Docker Hub is a scratch container with only the binary as entrypoint. For our use case (long-running server holding views, init.sql, shell-driven keep-alive) we add a thin debian layer that copies the binary out of the official image and bakes the `quack` + `httpfs` extensions at build time. See `k8s/Dockerfile`.

## Olive simulator (cmd/olive-sim)

A small Go HTTP gateway that mirrors what production Olive will do: accept typed REST requests, translate them into SQL with the caller's `org_id` baked into the WHERE clause, send the SQL to the Quack server, return JSON.

```
make serve                # or make kind-portforward, in another shell
./bin/olive-sim &         # listens on :8080

curl -s localhost:8080/healthz
curl -s localhost:8080/api/v1/schema
curl -s localhost:8080/api/v1/org_test_alpha/services
curl -s localhost:8080/api/v1/org_test_beta/services
curl -s 'localhost:8080/api/v1/org_test_demo/traces/count?since_days=15'
curl -s localhost:8080/api/v1/org_test_alpha/attributes/cloud.platform/distribution
```

Per-org enforcement is the entire point: the `{org_id}` segment is regex-validated then inlined into the SQL. There is no body or query string that lets a caller change the target org. The same protection covers the attribute-key segment of the distribution endpoint.

Injection attempts are rejected at validation:

```
$ curl -s "localhost:8080/api/v1/org'%20OR%201=1--/services"
{"error": "invalid org_id"}

$ curl -s "localhost:8080/api/v1/org_test_alpha/attributes/bad%20key%3B%20DROP/distribution"
{"error": "invalid attribute key"}
```

### Go-client compatibility note

The first attempt embedded DuckDB via `github.com/marcboeker/go-duckdb/v2`. Two compatibility issues surfaced:

- The static-linked binding does not surface the SecretType registration API to runtime-loaded extensions, so `CREATE SECRET (TYPE quack, …)` fails with `Secret type 'quack' not found`.
- The bundled DuckDB version is `1.4.1`. The Quack extension built for that version exposes only `quack` and `quack_openssl_version`; the `quack_query` table function we rely on is from a later Quack release that targets DuckDB `1.5+`.

For the POC we shell out to the system `duckdb` binary instead. Production Olive will need either a newer go-duckdb release (one that bundles DuckDB 1.5+) or a different binding strategy. The gap is also referenced in `M1-FINDINGS.md` and was commented onto card E-2462.

## Caveats

- **No auth chain validation**. The smoke flow uses a hard-coded `spike_token`. Wave 1 of the project will design the real auth chain (Cloudflare Tunnel + Access + WIF + Secret Manager).
- **Single Quack token**. Per-org tokens (M1 isolation model) are not exercised here; that decision is open.
- **macOS arm64 only tested**. DuckDB 1.5.3 with the Quack extension from `extensions.duckdb.org`.
- **No production traffic**. Fixture rows per signal: 50 traces, 100 logs, 200 gauge/sum, 50 histogram per (org, date).
